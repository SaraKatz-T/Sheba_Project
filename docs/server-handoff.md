# הנחיות לשרת הפייתון – חיבור ללקוח קליטת הטפסים

המסמך מיועד למי שבונה את שכבת הבקשות בשרת הפייתון. הוא מסביר מה הלקוח כבר עושה, ומה השרת צריך לממש כדי שהלקוח יעבוד מולו בלי שינויים.

**מקור האמת הוא `api-contract.md` (גרסה 2).** המסמך הזה מסכם אותו ומוסיף המלצות מימוש. אם יש סתירה, החוזה קובע.

## הקשר

- הפרויקט: מערכת לקליטת טפסי התחייבות של המעבדה המרכזית לנגיפים בשיבא (האקתון "קוד פתוח" 2026, גמר ב-28.10).
- **הלקוח** (React) נבנה בנפרד ומדבר עם השרת רק דרך ה-API שבחוזה. הוא לא שומר נתונים בדפדפן: הכל מגיע מהשרת ונשאר בזיכרון הדף עד היציאה.
- **כרגע הלקוח רץ מול שרת מדומה** שמממש את החוזה אחד לאחד. המעבר לשרת האמיתי הוא שינוי של שתי הגדרות בלקוח, בלי שינוי קוד.
- **החילוץ כבר קיים בשרת** (Gemini כקורא ראשי, Qwen כאימות שני, בדיקת ת"ז לפי ספרת ביקורת, סימון שדות לא ודאיים). לא משנים את הלוגיקה שלו. מה שחסר הוא השכבה שמסביב: בקשות, תור, מסד נתונים ועדכונים חיים.
- **לא משנים שמות שדות או מבנים בחוזה** בלי תיאום. הלקוח תלוי בהם בדיוק. אם משהו בחוזה לא אפשרי, מסמנים את זה ושואלים, ולא מאלתרים.

## המושג המרכזי: קובץ ≠ טופס

משתמש מעלה **קובץ** (Upload). קובץ יכול להכיל כמה **טפסים** (Form), למשל PDF סרוק של 12 עמודים עם 4 טפסים. השרת מפצל את הקובץ, יוצר טופס לכל קבוצת עמודים, ושומר לכל טופס את `upload_id` ואת `upload_pages`.

```
קובץ:  queued ─▶ splitting ─▶ processing ─▶ done
                      │                      (failed: רק אם הקובץ עצמו לא נקרא)
                      ▼
טופס:          received ─▶ processing ─▶ pending_review ─▶ approved / rejected
                                    └──▶ failed (לא מכשיל את הקובץ)
```

## ארכיטקטורה מומלצת

```
דפדפן ──HTTPS──▶ FastAPI ──▶ Redis (תור) ──▶ עובדים: פיצול / חילוץ טופס
   ▲                                              │
   └── WebSocket /api/live ◀── Redis pub/sub ◀────┘
```

- ה-API **רק** בודק את הקובץ, שומר אותו, מכניס משימה לתור ועונה מיד `202`. כך מאות קבצים יחד לא מפילים אותו.
- **שני סוגי משימות:** "פיצול קובץ" ו"חילוץ טופס". מספר העובדים קובע כמה קריאות למודלים רצות במקביל (מגבלות קצב).
- משימה שנפלה בגלל קריסה חוזרת לתור (RQ/arq/Celery עם retry).
- **עדכונים חיים:** העובדים רצים בתהליך נפרד, ולכן כל שינוי מתפרסם בערוץ Redis pub/sub. תהליך ה-API מאזין לערוץ ושולח לכל חיבורי ה-WebSocket.
- ספריות: RQ או arq (אסינכרונית, מתאימה ל-FastAPI), או Celery אם כבר בשימוש.

## מה לבנות, לפי הסדר

### 1. כניסה

- `POST /api/auth/login`, `POST /api/auth/logout`, `GET /api/auth/session`.
- הסיסמה ב-`.env` (למשל `APP_PASSWORD`). השוואה עם `hmac.compare_digest`, והגבלת ניסיונות (429).
- עוגייה: `HttpOnly; Secure; SameSite=Strict; Path=/api`, תוקף 8 שעות. בפיתוח על `http://localhost` אפשר בלי `Secure`.

### 2. קליטת קבצים

הבקשה `POST /api/uploads` מקבלת multipart עם `file`, `sha256`, `source` ו-`force`. מה השרת עושה:

1. בדיקת סוג לפי התוכן (magic bytes): PDF, JPEG, PNG, TIFF, HEIC/HEIF, WEBP. אחרת `415`.
2. עד 25MB, אחרת `413`. קובץ ריק: `400`.
3. חישוב SHA-256 בשרת והשוואה ל-`sha256` שנשלח.
4. אם קובץ עם אותו SHA-256 כבר קיים ולא נשלח `force=true`: `409` עם `existing_upload` (`id`, `file_name`, `received_at`).
5. שמירת הקובץ מחוץ לתיקייה ציבורית, יצירת Upload בסטטוס `queued`, הכנסה לתור.
6. תשובה `202` עם ה-Upload המלא, כולל `queue_position` ו-`eta_at`.

### 3. תור ועובדים

**פיצול קובץ:**
- `status = splitting`, שליחת עדכון.
- קריאת העמודים (PDF/TIFF: כל העמודים; תמונה: עמוד אחד) ומילוי `page_count`.
- זיהוי גבולות בין טפסים (לוגיקת הפיצול שכבר קיימת בשרת).
- יצירת Form לכל טופס: `status = received`, `upload_pages`, `page_count`, `file_name`, `source`, `received_at` מועתקים מהקובץ.
- בקובץ: `form_count`, `form_ids`, `status = processing`, `eta_at`. שליחת עדכון לקובץ ולכל טופס.
- הכנסת משימת "חילוץ טופס" לכל טופס.
- אם הקובץ לא נקרא (פגום, מוצפן, ריק): `status = failed`, `error` בעברית פשוטה.

**חילוץ טופס:**
- הרצת הצינור הקיים (Gemini, Qwen, ספרת ביקורת).
- **התקדמות:** עדכון `progress` (`percent`, `step`) בכל שלב, עם שמות בעברית. אלה השמות שהלקוח מציג היום: `שיפור תמונה`, `קריאה ראשונה (Gemini)`, `אימות שני (Qwen)`, `בדיקת ספרת ביקורת`.
- שמירת השדות במבנה Field שבחוזה: `value`, `confidence`, `uncertain`, `reason_code`, `reason` (משפט בעברית, למשל `Gemini קרא X ו-Qwen קרא Y`), `readings`, `box`.
- **קואורדינטות:** Gemini מחזיר `box_2d = [ymin, xmin, ymax, xmax]` בסקאלה 0–1000. ממירים ל-`{page, x: xmin/1000, y: ymin/1000, w: (xmax-xmin)/1000, h: (ymax-ymin)/1000}`, כש-`page` הוא מספר העמוד **בתוך הטופס** (מתחיל ב-1).
- מילוי `person_name`, `id_number`, `form_date` (ISO) ו-`uncertain_count` בטופס.
- `status = pending_review`, או `failed` עם `error` בעברית. כשל של טופס לא מכשיל את הקובץ.
- כשכל הטפסים של הקובץ הגיעו ל-`pending_review` או `failed`: הקובץ עובר ל-`done`, ו-`eta_at = null`.

**זמן משוער (`eta_at`):** `עכשיו + (טפסים שנשארו בתור ÷ מספר עובדים) × זמן ממוצע לטופס`. הזמן הממוצע הוא ממוצע נע על הטפסים האחרונים. לפני הפיצול אפשר להעריך לפי מספר העמודים. מחשבים מחדש בכל שינוי ושולחים עדכון.

**מקום בתור (`queue_position`):** כמה קבצים לפניו בתור הפיצול (1 = הבא). מעדכנים את כל הקבצים שממתינים בכל פעם שהתור זז.

### 4. עדכונים חיים – WebSocket `/api/live`

- ב-handshake: בדיקת עוגיית הכניסה **ובדיקה שכותרת `Origin` היא כתובת הלקוח**. בלי כניסה סוגרים עם קוד `4401`.
- השרת שולח הודעות JSON, והלקוח לא שולח כלום:
  - `{"type": "upload.updated", "upload": {...Upload מלא}}`
  - `{"type": "form.updated", "form": {...FormSummary מלא}}`
- **תמיד את האובייקט המלא**, לא רק מה שהשתנה.
- **מתי שולחים:** בכל שינוי בקובץ או בטופס, כולל תיקון שדה, אישור, דחייה, מיזוג, ושינויים שהגיעו מהטלפון או ממסך אחר.
- **לכל המחוברים:** אין משתמשים נפרדים.
- עדכוני `progress` לכל היותר פעמיים בשנייה לטופס.
- ping ברמת הפרוטוקול כל 20–30 שניות. ב-uvicorn/websockets זו ברירת המחדל.
- ביציאה (logout) סוגרים את החיבורים של הסשן עם `4401`.
- **הלקוח טוען מחדש את הרשימות אחרי כל התחברות**, כך שאין צורך לשמור היסטוריית הודעות.

### 5. קריאה

- `GET /api/uploads`: קבצים מ-24 השעות האחרונות, מהחדש לישן.
- `GET /api/uploads/{id}`.
- `GET /api/forms`: כל הטפסים (`FormSummary`), מהחדש לישן. הלקוח מחשב בעצמו חיפוש, סינון, מדדים ולוח שנה.
- `GET /api/forms/{id}`: `FormDetail` עם `pages` ו-`fields`.
- `GET /api/forms/{id}/pages/{n}/image`: PNG או JPEG. PDF מרנדרים לתמונה (למשל PyMuPDF), ו-HEIC/TIFF ממירים (Pillow + pillow-heif).

### 6. בדיקה ואישור

- `PATCH /api/forms/{id}/fields/{key}` עם `{value, source}`. בתיקון הראשון שומרים את הערך הקודם ב-`original_value`. `uncertain = false`, ו-`corrected` לפי השוואה ל-`original_value`. `source = confirmed` משאיר את הערך ורק מאשר.
- `POST /api/forms/{id}/approve`: רק מ-`pending_review` (אחרת `409`). מעדכן `reviewed_at`.
- `POST /api/forms/{id}/reject` עם `reason` לא חובה.
- `POST /api/forms/{id}/retry`: טופס `failed` חוזר לתור החילוץ (בלי פיצול מחדש).
- `POST /api/uploads/{id}/retry`: קובץ `failed` חוזר לתור הפיצול.
- `POST /api/forms/{id}/merge` עם `{into, values}`.

### 7. צילום מהטלפון

- `POST /api/capture-sessions` (דורש כניסה): `token` אקראי (`secrets.token_urlsafe(32)`), תוקף 10 דקות.
- `GET /api/capture/{token}`: `200` / `404` / `410`.
- `POST /api/capture/{token}/uploads`: כמו `POST /api/uploads` עם `source = phone`. מחזיר רק `{id, status}`, בלי נתונים אישיים.

## מסד נתונים (הצעה)

- **uploads:** כל שדות ה-Upload, ונתיב הקובץ בדיסק.
- **forms:** כל שדות ה-FormSummary. `upload_pages` כ-JSON.
- **fields:** `form_id`, `key`, `label`, `type`, `value`, `confidence`, `uncertain`, `reason_code`, `reason`, `readings` (JSON), `box` (JSON), `corrected`, `original_value`, `position` (לשמירת הסדר).
- **capture_sessions:** `token`, `expires_at`.

SQLite מספיק להאקתון. מומלץ להפעיל WAL כי העובדים כותבים במקביל.

## אבטחה – רשימת בדיקה

- [ ] HTTPS / WSS בסביבה אמיתית.
- [ ] הסיסמה ומפתחות ה-API רק ב-`.env`, ו-`.env` ב-`.gitignore`.
- [ ] עוגייה `HttpOnly; Secure; SameSite=Strict`.
- [ ] בדיקת `Origin` ב-WebSocket.
- [ ] `Cache-Control: no-store` על כל תשובה עם נתונים אישיים ועל כל תמונה.
- [ ] בדיקת קבצים לפי magic bytes, ומגבלת 25MB.
- [ ] בלי שמות, מספרי ת"ז, ערכי שדות או תוכן קבצים בלוגים.
- [ ] **כל שגיאה בגוף JSON:** `{"error": {"code", "message"}}`. גם 404. 404 בלי הגוף הזה הלקוח מפרש כ"כתובת שרת שגויה".
- [ ] אותו מקור ללקוח ולשרת (השרת מגיש את `dist/` של הלקוח, או reverse proxy משותף), כך שאין צורך ב-CORS.

## בדיקה מול הלקוח

1. בלקוח, בקובץ `.env`:
   ```
   VITE_USE_MOCK=false
   VITE_API_URL=http://localhost:8000
   ```
2. `npm run dev` בתיקיית הלקוח, ופתיחת http://localhost:5173. Vite מעביר את `/api` לשרת, כולל ה-WebSocket.
3. בשרת: עמוד `/docs` של FastAPI. מומלץ להגדיר מודלי Pydantic שתואמים בדיוק למבנים בחוזה, כך שהתיעוד החי נכון.
4. **מה בודקים:**
   - כניסה.
   - גרירה של כמה קבצים, ביניהם PDF עם כמה טפסים: הלקוח אמור להציג "נשלח לעיבוד · מקום N בתור", אחר כך "מפצל לטפסים", אחר כך את רשימת הטפסים עם התקדמות וזמן משוער.
   - העלאה חוזרת של אותו קובץ: אזהרת כפילות.
   - קובץ פגום: "נכשל" עם "לנסות שוב".

**מסכים שעוד ייבנו בלקוח**, ויתבססו על אותו חוזה: רשומות, בדיקה ואישור (שדות צהובים, קטע מוגדל לפי `box`), ייצוא, מדדים ולוח שנה, צילום מהטלפון ומצב הדגמה.
